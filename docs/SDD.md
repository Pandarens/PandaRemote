# PandaRemoteControl — Software Design Document

Версия: 0.2 · Дата: 2026-10-21

## 1. Цель

Личный инструмент удалённого доступа к своему ПК (аналог TeamViewer/AnyDesk) и **игрового стриминга** (в т.ч. с телефона) с требованиями:

| # | Требование |
|---|---|
| R1 | Подключение к ПК с **динамическим IP** и за NAT, без проброса портов и без DDNS |
| R2 | **Нет базы пользователей**, регистрации и аккаунтов. Доступ определяется только ключом |
| R3 | Адрес компьютера **не меняется** с точки зрения клиента: один раз сохранил — подключаешься всегда |
| R4 | Соединение **peer-to-peer** со сквозным шифрованием; промежуточные узлы не видят трафик |
| R5 | Рабочий стол: просмотр экрана + управление мышью/клавиатурой |
| R6 | Журнал подключений на удалённом ПК |
| R7 | **Игры**: низкая задержка, аппаратное кодирование, геймпад, звук |
| R8 | **Телефон** как клиент (Android, затем iOS) |

## 2. Ключевая идея: адрес = публичный ключ

Компьютер идентифицируется не IP-адресом, а **публичным ключом Ed25519** (`EndpointId`), который генерируется один раз и хранится локально. IP может меняться сколько угодно — ключ остаётся прежним.

Сетевой слой — библиотека [iroh](https://iroh.computer) 1.4 (Rust, QUIC с multipath и NAT traversal):

```
 Клиент                                                    Хост (удалённый ПК)
 знает: EndpointId хоста + секрет                          знает: свой SecretKey + секрет
        │                                                         │
        │ 1. "где сейчас EndpointId X?"   ┌──────────────────┐    │ публикует каждые N минут
        └────────────────────────────────►│ Address lookup   │◄───┘ подписанную запись:
                                          │ (pkarr / DNS)    │      {relay URL, IP:порты}
        ◄──── подписанная запись ─────────└──────────────────┘
        │ 2. QUIC через relay (работает сразу, за любым NAT)
        ├───────────────────► Relay ─────────────────────────────────►│
        │ 3. параллельно — UDP hole punching
        └══════════════ прямое P2P-соединение ═══════════════════════►│
```

* **Address lookup** хранит лишь подписанную ключом хоста запись «где я сейчас». Подделать её нельзя; это не база пользователей.
* **Relay** нужен для первичного рукопожатия и как запасной канал, если hole punching не удался. Пересылает только зашифрованные пакеты.
* При смене IP хоста посреди сессии QUIC мигрирует путь без разрыва.

### 2.1 Инфраструктура и независимость

| Этап | Lookup | Relay | Зависимость от третьих лиц |
|---|---|---|---|
| сейчас | публичный n0 DNS/pkarr | публичные relay n0 | бесплатная инфраструктура n0, без регистрации |
| v2 | + Mainline DHT (BitTorrent, BEP44) | свой `iroh-relay` на VPS (опционально) | ноль |

## 3. Модель доступа («синхронизация по ключу»)

### 3.1 Файлы

Каталог: `%APPDATA%\PandaRC\config\` (или `$PANDA_HOME`).

| Файл | Сторона | Содержимое |
|---|---|---|
| `host.key` | хост | Ed25519 SecretKey — постоянный «адрес» ПК |
| `host.json` | хост | `access_secret` (32 случайных байта), имя, базовый порт Sunshine |
| `connections.log` | хост | журнал подключений (JSON Lines) |
| `client.key` | клиент | ключ клиента (стабильный ID в журнале хоста) |
| `hosts.json` | клиент | сохранённые компьютеры: имя + билет |

### 3.2 Билет подключения (ticket)

```
panda1<base32( host_endpoint_id[32] || access_secret[32] )>
```

Одна строка (~110 символов), которую один раз переносят на клиент. Её достаточно, чтобы подключаться всегда, где бы ни был хост. Билет = пароль. `panda-rc host --rotate-secret` (или кнопка в GUI) делает все старые билеты недействительными, сохраняя адрес ПК.

### 3.3 Аутентификация

QUIC/TLS уже взаимно аутентифицирует стороны по ключам. Поверх — challenge-response без передачи секрета:

```
Клиент → Хост : Hello { version, client_name, kind: Desktop | GameTunnel }
Хост → Клиент : Challenge { nonce[32], host_name }
Клиент → Хост : Auth { mac = BLAKE3-keyed(secret, "panda-rc auth v1" || nonce || client_id || host_id) }
Хост → Клиент : AuthResult { ok, reason }
```

Привязка MAC к обоим ID исключает replay/relay-атаки. Неудачная попытка → пауза 2 с + запись `auth_failed` в журнал.

## 4. Архитектура

Один бинарник `panda-rc.exe` на Rust, два режима поверх общего P2P-ядра:

```
                 ┌──────────────────────── Panda core ────────────────────────┐
                 │ ключи · билет · auth · iroh endpoint · журнал              │
                 └───────────────┬───────────────────────────┬────────────────┘
          режим «Рабочий стол»   │                           │  режим «Игры»
   ┌─────────────────────────────▼──────┐   ┌────────────────▼─────────────────────────┐
   │ DXGI-захват → H.264 (openh264)     │   │ TCP/UDP туннель                           │
   │ ввод мыши/клавиатуры (SendInput)   │   │ Moonlight ⇄ 127.0.0.1 ⇄ P2P ⇄ Sunshine    │
   │ свой viewer (egui)                 │   │ (NVENC/AMF, геймпады, звук — у Sunshine) │
   └────────────────────────────────────┘   └───────────────────────────────────────────┘
```

### 4.1 Команды

| Команда | Что делает |
|---|---|
| `panda-rc` | GUI: «Подключения» (мои ПК, кнопки 🖥/🎮) и «Этот компьютер» (хост, билет, журнал) |
| `panda-rc host [--rotate-secret]` | headless-хост (для автозапуска) |
| `panda-rc ticket` | показать билет |
| `panda-rc connect <ticket>` | открыть окно рабочего стола |
| `panda-rc game <ticket>` | поднять игровой туннель (CLI) |
| `panda-rc log` | журнал подключений |
| `panda-rc probe <ticket>` | диагностика: принять видео, сохранить кадр в PNG |

### 4.2 Модули

```
src/
  main.rs            CLI
  config.rs          ключи, host.json, hosts.json, журнал
  ticket.rs          билет
  proto.rs           сообщения, фрейминг (u32 len + postcard), MAC, настройка endpoint
  tunnel.rs          игровой туннель (обе стороны)
  host/mod.rs        приём соединений, auth, диспетчеризация по SessionKind
  host/desktop.rs    сессия рабочего стола
  host/dxgi.rs       захват DXGI Desktop Duplication
  host/capture.rs    источник кадров (DXGI → fallback GDI) + H.264
  host/input.rs      инъекция ввода (enigo)
  client/mod.rs      подключение + auth, общий endpoint процесса
  client/viewer.rs   приём/декодирование видео, отправка ввода
  gui.rs             eframe/egui интерфейс
```

### 4.3 Режим «Рабочий стол»

Одно QUIC-соединение, ALPN `panda-rc/1`:

| Поток | Направление | Содержимое |
|---|---|---|
| bi-stream «control» | ↔ | auth, затем `Input`/`RequestKeyframe` (клиент) и `ScreenInfo` (хост) |
| uni-stream «video» | хост → клиент | `VideoFrame { width, height, keyframe, data (H.264 Annex B) }` |

* **Захват**: DXGI Desktop Duplication (кадр только при изменении экрана, ~1 мс). Если недоступен — GDI (медленно). При потере дубликации (UAC, экран блокировки, смена режима) — переоткрытие каждые 0,5 с.
* **Кодирование**: openh264, профиль screen content, 8 Мбит/с, ≤30 к/с, IDR каждые 5 с и по запросу клиента. Экраны шире 2560 px уменьшаются в целое число раз.
* **Backpressure**: канал ёмкостью 1 между захватом и сетью — при медленной сети падает fps, а не растёт задержка.
* **Ввод**: координаты нормализованы (0..65535) к кадру; печатный текст — `Text` (любая раскладка); спец-клавиши и шорткаты — `Key` с модификаторами; Ctrl+V в окне клиента вводит текст из буфера клиента.

### 4.4 Режим «Игры» (Sunshine + Moonlight)

**Почему не свой стример.** Игровой стриминг требует аппаратного кодирования (NVENC/AMF/QuickSync), виртуальных геймпадов (ViGEm), захвата звука, FEC и задержки < 10 мс. Это уже решено в [Sunshine](https://github.com/LizardByte/Sunshine) (сервер) и [Moonlight](https://github.com/moonlight-stream) (клиенты для Windows/macOS/Linux/Android/iOS/TV). Чего у них нет — подключения без IP/проброса портов. Это и даёт Panda.

```
 Moonlight ──► 127.0.0.1:47984/47989/48010 (TCP), 47998-48000 (UDP)
    │               │ Panda-клиент
    │               ▼
    │        QUIC bi-streams (TCP) + QUIC datagrams (UDP) — P2P, E2E-шифрование
    │               │ Panda-хост
    │               ▼
    └──────► Sunshine 127.0.0.1:<base>…
```

* Порты GameStream (по исходникам Sunshine): TCP `base-5` (HTTPS), `base` (HTTP), `base+1` (веб-панель), `base+21` (RTSP); UDP `base+9` (видео), `+10` (control), `+11` (аудио), `+13` (микрофон). По проводу передаются **смещения**, поэтому базовый порт Sunshine на хосте может быть любым (`host.json → sunshine_port`), а клиент всегда слушает стандартные порты.
* **TCP** → отдельный QUIC bi-stream на каждое соединение.
* **UDP** → QUIC datagrams. Moonlight считает 127.0.0.1 локальной сетью и шлёт пакеты ~1400 байт, а MTU датаграммы меньше, поэтому применяется фрагментация: заголовок `offset i16 | id u16 | idx u8 | count u8`. Потеря фрагмента = потеря пакета (как в обычном UDP; FEC Moonlight это переживает).
* Буферы: UDP-сокеты туннеля 4 МБ (дефолт Windows 64 КБ теряет пачки видео), очереди датаграмм QUIC 8 МБ.
* Сопряжение Moonlight с Sunshine (PIN) делается один раз через веб-панель Sunshine, которая тоже доступна через туннель (`https://127.0.0.1:47990`).

### 4.5 Телефон

| Платформа | Игры | Рабочий стол |
|---|---|---|
| Android | Moonlight Android + приложение **Panda Android**: foreground-сервис, поднимающий тот же туннель на 127.0.0.1 (Rust-ядро через JNI/UniFFI, `cargo-ndk`) | viewer в том же приложении (egui/Compose + декодер MediaCodec) |
| iOS | Moonlight iOS + Panda iOS в виде **Network Extension** (фоновая работа обычного приложения на iOS ограничена) | позже |

Ядро (`config/ticket/proto/tunnel/client`) не зависит от Windows и переиспользуется на мобильных платформах.

## 5. Безопасность

| Угроза | Защита |
|---|---|
| Прослушивание (провайдер, relay) | QUIC TLS 1.3, сквозное шифрование |
| Подмена хоста | соединение по EndpointId — TLS проверяет ключ хоста |
| Подмена записи «где хост» | запись подписана ключом хоста |
| Подбор секрета | 256 бит энтропии + пауза после неудачи |
| Утечка билета | смена секрета; журнал показывает все попытки |
| Доступ к портам Sunshine через туннель | хост пускает только к 127.0.0.1 и только на 8 портов GameStream |
| Утечка секрета в логи | `Debug` обработчика хоста не печатает секрет |

## 6. Ограничения текущей версии

* Хост работает в сессии пользователя: на **экране блокировки** и в окнах **UAC** DXGI недоступен (только SYSTEM-процесс), ввод пароля Windows удалённо невозможен. План: служба Windows + helper в активной сессии.
* Курсор удалённого ПК в кадр не рисуется (виден локальный курсор клиента).
* Один (основной) монитор; при смене разрешения нужно переподключиться.
* Две копии клиента на одном ПК делят `client.key` и мешают друг другу на relay — используйте одну.

## 7. План развития

1. ✅ Ядро: ключи, билет, auth, журнал. ✅ Рабочий стол (DXGI + H.264 + ввод). ✅ Игровой туннель для Moonlight/Sunshine.
2. Android-приложение (туннель для Moonlight + viewer).
3. Служба Windows (экран блокировки/UAC), автозапуск, трей.
4. Mainline DHT lookup + опциональный свой relay → полная независимость от n0.
5. Буфер обмена в обе стороны, передача файлов, выбор монитора, аппаратный энкодер для режима «Рабочий стол».
6. iOS.
