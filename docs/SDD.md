# PandaRemoteControl — Software Design Document

Версия: 0.3 · Дата: 2026-10-21

## 1. Цель

Личный инструмент удалённого доступа к своему ПК (аналог TeamViewer/AnyDesk) и **игрового стриминга** (в т.ч. с телефона). Всё — собственная реализация, без Sunshine/Moonlight/Parsec. Требования:

| # | Требование |
|---|---|
| R1 | Подключение к ПК с **динамическим IP** и за NAT, без проброса портов и без DDNS |
| R2 | **Нет базы пользователей**, регистрации и аккаунтов. Доступ определяется только ключом |
| R3 | Адрес компьютера **не меняется** с точки зрения клиента: один раз сохранил — подключаешься всегда |
| R4 | Соединение **peer-to-peer** со сквозным шифрованием; промежуточные узлы не видят трафик |
| R5 | Рабочий стол: просмотр экрана + управление мышью/клавиатурой |
| R6 | Журнал подключений на удалённом ПК |
| R7 | **Игры**: 60+ к/с, задержка ≲ 20 мс в LAN, аппаратное кодирование, геймпад, звук |
| R8 | **Телефон** как клиент (Android, затем iOS) |

## 2. Ключевая идея: адрес = публичный ключ

Компьютер идентифицируется не IP-адресом, а **публичным ключом Ed25519** (`EndpointId`), который генерируется один раз и хранится локально. IP может меняться сколько угодно — ключ остаётся прежним.

Сетевой слой — библиотека [iroh](https://iroh.computer) 1.4 (Rust, QUIC с multipath и NAT traversal):

```
 Клиент                                                    Хост (удалённый ПК)
 знает: EndpointId хоста + секрет                          знает: свой SecretKey + секрет
        │                                                         │
        │ 1. "где сейчас EndpointId X?"   ┌──────────────────┐    │ публикует каждые N минут
        └────────────────────────────────►│ Address lookup   │◄───┘ подписанную запись:
                                          │ (pkarr / DNS)    │      {relay URL, IP:порты}
        ◄──── подписанная запись ─────────└──────────────────┘
        │ 2. QUIC через relay (работает сразу, за любым NAT)
        ├───────────────────► Relay ─────────────────────────────────►│
        │ 3. параллельно — UDP hole punching
        └══════════════ прямое P2P-соединение ═══════════════════════►│
```

* **Address lookup** хранит лишь подписанную ключом хоста запись «где я сейчас». Подделать её нельзя; это не база пользователей.
* **Relay** нужен для первичного рукопожатия и как запасной канал, если hole punching не удался. Пересылает только зашифрованные пакеты.
* При смене IP хоста посреди сессии QUIC мигрирует путь без разрыва.

### 2.1 Инфраструктура и независимость

| Этап | Lookup | Relay | Зависимость от третьих лиц |
|---|---|---|---|
| сейчас | публичный n0 DNS/pkarr | публичные relay n0 | бесплатная инфраструктура n0, без регистрации |
| v2 | + Mainline DHT (BitTorrent, BEP44) | свой `iroh-relay` на VPS (опционально) | ноль |

## 3. Модель доступа («синхронизация по ключу»)

### 3.1 Файлы

Каталог: `%APPDATA%\PandaRC\config\` (или `$PANDA_HOME`).

| Файл | Сторона | Содержимое |
|---|---|---|
| `host.key` | хост | Ed25519 SecretKey — постоянный «адрес» ПК |
| `host.json` | хост | `access_secret` (32 случайных байта), имя |
| `connections.log` | хост | журнал подключений (JSON Lines) |
| `client.key` | клиент | ключ клиента (стабильный ID в журнале хоста) |
| `hosts.json` | клиент | сохранённые компьютеры: имя + билет |

### 3.2 Билет подключения (ticket)

```
panda1<base32( host_endpoint_id[32] || access_secret[32] )>
```

Одна строка (~110 символов), которую один раз переносят на клиент. Её достаточно, чтобы подключаться всегда, где бы ни был хост. Билет = пароль. `panda-rc host --rotate-secret` (или кнопка в GUI) делает все старые билеты недействительными, сохраняя адрес ПК.

### 3.3 Аутентификация

QUIC/TLS уже взаимно аутентифицирует стороны по ключам. Поверх — challenge-response без передачи секрета:

```
Клиент → Хост : Hello { version, client_name, profile: Desktop | Game }
Хост → Клиент : Challenge { nonce[32], host_name }
Клиент → Хост : Auth { mac = BLAKE3-keyed(secret, "panda-rc auth v1" || nonce || client_id || host_id) }
Хост → Клиент : AuthResult { ok, reason }
```

Привязка MAC к обоим ID исключает replay/relay-атаки. Неудачная попытка → пауза 2 с + запись `auth_failed` в журнал.

## 4. Архитектура

Один бинарник `panda-rc.exe` на Rust. Один движок стриминга **Panda Stream** с двумя профилями:

| | Профиль «Рабочий стол» | Профиль «Игра» |
|---|---|---|
| Частота кадров | до 30 | 60 |
| Битрейт | 8 Мбит/с | 20 Мбит/с, адаптивный (5–50) |
| Мышь | абсолютная (курсор клиента) | относительная, курсор захвачен окном |
| Клавиатура | текст + шорткаты | сканкоды (как физическая клавиатура) |
| Геймпад / звук | — / да | да / да |

```
 ХОСТ                                                                 КЛИЕНТ
 DXGI Desktop Duplication ─► BGRA→NV12 ─► H.264 HW (Media Foundation:   QUIC datagrams ─► сборка кадра
   (кадр только при изменении)            QuickSync / NVENC / AMF;      + Reed-Solomon FEC   + восстановление FEC
                                           fallback openh264)                     │            ─► декодер H.264
 WASAPI loopback ─► Opus 20 мс ──────────────────────────► QUIC datagrams ─► Opus ─► динамики
 SendInput (сканкоды, отн. мышь) ◄── control stream ◄───── ввод: клавиатура, мышь, геймпад (gilrs)
 ViGEmBus (виртуальный Xbox 360) ◄─┘
```

### 4.1 Команды

| Команда | Что делает |
|---|---|
| `panda-rc` | GUI: «Подключения» (мои ПК, кнопки 🖥 Рабочий стол / 🎮 Игра) и «Этот компьютер» (хост, билет, журнал) |
| `panda-rc host [--rotate-secret]` | headless-хост (для автозапуска) |
| `panda-rc ticket` | показать билет |
| `panda-rc connect <ticket> [--game]` | открыть окно сеанса |
| `panda-rc log` | журнал подключений |
| `panda-rc probe <ticket> [--game]` | диагностика: принять видео, сохранить кадр в PNG, показать fps и потери |

### 4.2 Модули

```
src/
  main.rs              CLI
  config.rs            ключи, host.json, hosts.json, журнал
  ticket.rs            билет
  proto.rs             сообщения, фрейминг, MAC, настройка endpoint
  media/fec.rs         нарезка кадров на датаграммы + Reed-Solomon
  host/mod.rs          приём соединений, auth
  host/session.rs      конвейер сеанса: захват → кодек → отправка, приём ввода
  host/dxgi.rs         захват DXGI Desktop Duplication
  host/capture.rs      источник кадров (DXGI → fallback GDI)
  host/encoder/        mf.rs — аппаратный H.264 (Media Foundation); sw.rs — openh264
  host/input.rs        SendInput: абсолютная/относительная мышь, сканкоды, текст
  host/gamepad.rs      виртуальный Xbox 360 через ViGEmBus
  host/audio.rs        WASAPI loopback + Opus
  client/mod.rs        подключение + auth
  client/viewer.rs     приём видео/звука, сборка кадров, отправка ввода и статистики
  client/decoder/      mf.rs — DXVA-декодер (Media Foundation); sw.rs — openh264
  yuv_render.rs        отрисовка NV12 шейдером wgpu в egui
  gui.rs               eframe/egui интерфейс
```

### 4.3 Соединение и каналы

Одно QUIC-соединение, ALPN `panda-rc/2`:

| Канал | Направление | Содержимое |
|---|---|---|
| bi-stream «control» (надёжный) | ↔ | auth; `Input`, `Gamepad`, `RequestKeyframe`, `Stats` (клиент); `StreamInfo` (хост) |
| datagrams, тип `0x01` | хост → клиент | шарды видеокадров с FEC |
| datagrams, тип `0x02` | хост → клиент | пакеты Opus (20 мс) |

### 4.4 Видео

* **Захват**: DXGI Desktop Duplication — кадр только при изменении экрана, ~1 мс. Fallback GDI. При потере дубликации (UAC, блокировка, смена режима) — переоткрытие каждые 0,5 с.
* **Кодирование**: аппаратный H.264 через Media Foundation (асинхронный MFT, low-latency режим, CBR, IDR по запросу). Работает на Intel QuickSync, NVIDIA NVENC и AMD AMF через их MFT. Если аппаратного энкодера нет — openh264.
* **Транспорт**: кадр режется на шарды по размеру датаграммы, к ним добавляются Reed-Solomon parity-шарды (≈20 %, минимум 1). Заголовок шарда: `type u8 | frame_id u32 | idx u16 | data u16 | parity u16 | frame_len u32 | flags u8`. Клиент собирает кадр, как только пришли любые `data` шардов из `data+parity`.
* **Потери**: если кадр не собрался, а уже идёт следующий, — кадр отбрасывается, клиент шлёт `RequestKeyframe` (не чаще раза в 200 мс) и до IDR не декодирует.
* **Адаптивный битрейт**: клиент раз в секунду шлёт `Stats { frames, lost }`; хост снижает битрейт ×0,8 при потерях > 2 % и повышает ×1,1 после 5 с без потерь (в пределах профиля).
* **Декодирование**: Microsoft H.264 MFT, привязанный к D3D11-устройству (DXVA — декодирует видеочип); кадр копируется в staging-текстуру и читается одним Map. Если DXVA недоступен — openh264. Диагностика: `PANDA_DECODER=sw`.
* **Отрисовка**: кадр передаётся в GUI как NV12 (1,5 байта на пиксель), YUV→RGB (BT.601) считает фрагментный шейдер wgpu внутри egui. Без wgpu — конвертация на CPU и обычная текстура.

### 4.5 Ввод

* **Рабочий стол**: абсолютные координаты, нормализованные 0..65535; печатный текст — `Text`; спец-клавиши — `Key` с модификаторами.
* **Игра**: окно захватывает курсор, передаются сырые относительные смещения мыши → `SendInput(MOUSEEVENTF_MOVE)`; клавиши — по физическому положению → сканкоды `SendInput(KEYEVENTF_SCANCODE)`, это понимают игры на DirectInput/Raw Input. Выход из захвата: `Ctrl+Alt+Shift+Q`.
* **Геймпад**: клиент читает контроллеры через gilrs и шлёт состояние в раскладке XInput при каждом изменении; хост создаёт виртуальный Xbox 360 через драйвер **ViGEmBus** (единственный способ получить виртуальный XInput-контроллер в Windows; ставится один раз). Вибрация — обратным сообщением (позже).

### 4.6 Звук

WASAPI loopback (то, что звучит на хосте) → 48 кГц стерео → Opus (CELT, low-delay) 20 мс, 128 кбит/с → датаграммы `0x02 | seq u32 | opus`. На клиенте: джиттер-буфер 40 мс (обрезка выше 150 мс), маскировка до 5 потерянных пакетов средствами Opus PLC, вывод через cpal. Opus — чистая Rust-реализация (opus-rs), сборка без CMake.

### 4.7 Телефон

| Платформа | Клиент |
|---|---|
| Android | приложение Panda: Rust-ядро (сеть, auth, FEC, Opus) через JNI/UniFFI + Kotlin UI, декодирование MediaCodec, геймпады через Android InputDevice |
| iOS | позже: то же ядро + VideoToolbox |

Ядро (`config/ticket/proto/media/client`) не зависит от Windows.

### 4.8 Почему так

* **Датаграммы + FEC, а не надёжный поток**: при потере пакета надёжный поток ждёт ретрансмит (≥1 RTT) и задерживает все следующие кадры; FEC восстанавливает потерю сразу, а неисправимая потеря стоит одного IDR.
* **Media Foundation, а не NVENC/AMF SDK напрямую**: один API для всех трёх вендоров, без проприетарных SDK.
* **QUIC (iroh)** даёт шифрование, NAT traversal и congestion control.

## 5. Безопасность

| Угроза | Защита |
|---|---|
| Прослушивание (провайдер, relay) | QUIC TLS 1.3, сквозное шифрование |
| Подмена хоста | соединение по EndpointId — TLS проверяет ключ хоста |
| Подмена записи «где хост» | запись подписана ключом хоста |
| Подбор секрета | 256 бит энтропии + пауза после неудачи |
| Утечка билета | смена секрета; журнал показывает все попытки |
| Злоупотребление вводом | ввод принимается только после успешной аутентификации |
| Утечка секрета в логи | `Debug` обработчика хоста не печатает секрет |

## 6. Ограничения текущей версии

* Хост работает в сессии пользователя: на **экране блокировки** и в окнах **UAC** DXGI недоступен (нужен SYSTEM-процесс), ввод пароля Windows удалённо невозможен. План: служба Windows + helper в активной сессии.
* Курсор удалённого ПК в кадр не рисуется (в профиле «Рабочий стол» виден локальный курсор клиента).
* Один (основной) монитор; при смене разрешения нужно переподключиться.
* Геймпад требует установленного драйвера ViGEmBus на хосте.
* Две копии клиента на одном ПК делят `client.key` и мешают друг другу на relay.

## 7. План развития

1. ✅ Ядро: ключи, билет, auth, журнал. ✅ Рабочий стол (DXGI + H.264 + ввод).
2. Игровой профиль: аппаратный энкодер MF, датаграммы + FEC, 60 к/с, относительная мышь, сканкоды, геймпад, звук, адаптивный битрейт.
3. ✅ Аппаратное декодирование на клиенте. Вибрация геймпада.
4. Android-клиент.
5. Служба Windows (экран блокировки/UAC), автозапуск, трей.
6. Mainline DHT lookup + опциональный свой relay → полная независимость от n0.
7. Буфер обмена, передача файлов, выбор монитора, HEVC/AV1, iOS.

## 9. Проверено

| Проверка | Результат |
|---|---|
| Хост ↔ клиент через реальную сеть n0, P2P-путь | соединение ~1,1 с |
| Неверный билет | отказ «неверный ключ доступа», запись в журнале |
| Рабочий стол: видео 1920×1080 end-to-end | кадр получен и декодирован |
| Аппаратный энкодер (Intel QuickSync MFT), 1080p | 10 мс/кадр с конвертацией в NV12; openh264 — 82 мс |
| Декодер openh264 на клиенте, 1080p | 4,8 мс/кадр до NV12, ~8 мс CPU потока |
| Декодер DXVA (MF + D3D11), 1080p | 4,7 мс/кадр до NV12, ~2,5 мс CPU потока; кадры совпадают с openh264 (макс. разница 4/255) |
| Шейдер NV12→RGB, офскрин-рендер на GPU | цвет совпадает (юнит-тест) |
| FEC: потеря ~16 % шардов при 20 % parity | кадр восстановлен (юнит-тест) |
| Игровой профиль end-to-end, движущаяся картинка | 58–59 к/с, потери 0 %, кодирование 12,8 мс |
| Относительная мышь через SendInput | доходит до хоста (курсор сдвинут) |
| Нет драйвера ViGEmBus | хост сообщает клиенту «драйвер не установлен», клиент показывает предупреждение |
| Сканкоды клавиатуры, геймпад с драйвером | не проверено вживую |
| Звук: WASAPI loopback → Opus → датаграммы | пакеты доходят до клиента |
| Opus encode→decode (opus-rs), синус 440 Гц | уровень сохранён (юнит-тест) |
| Воспроизведение звука на отдельном клиенте | не проверено на слух (тест на одном ПК дал бы петлю) |
