# PandaRemoteControl — Software Design Document

Версия: 0.3 · Дата: 2026-10-21

## 1. Цель

Личный инструмент удалённого доступа к своему ПК (аналог TeamViewer/AnyDesk) и **игрового стриминга** (в т.ч. с телефона). Всё — собственная реализация, без Sunshine/Moonlight/Parsec. Требования:

| # | Требование |
|---|---|
| R1 | Подключение к ПК с **динамическим IP** и за NAT, без проброса портов и без DDNS |
| R2 | **Нет базы пользователей**, регистрации и аккаунтов. Доступ определяется только ключом |
| R3 | Адрес компьютера **не меняется** с точки зрения клиента: один раз сохранил — подключаешься всегда |
| R4 | Соединение **peer-to-peer** со сквозным шифрованием; промежуточные узлы не видят трафик |
| R5 | Рабочий стол: просмотр экрана + управление мышью/клавиатурой |
| R6 | Журнал подключений на удалённом ПК |
| R7 | **Игры**: 60+ к/с, задержка ≲ 20 мс в LAN, аппаратное кодирование, геймпад, звук |
| R8 | **Телефон** как клиент (Android, затем iOS) |

## 2. Ключевая идея: адрес = публичный ключ

Компьютер идентифицируется не IP-адресом, а **публичным ключом Ed25519** (`EndpointId`), который генерируется один раз и хранится локально. IP может меняться сколько угодно — ключ остаётся прежним.

Сетевой слой — библиотека [iroh](https://iroh.computer) 1.4 (Rust, QUIC с multipath и NAT traversal):

```
 Клиент                                                    Хост (удалённый ПК)
 знает: EndpointId хоста + секрет                          знает: свой SecretKey + секрет
        │                                                         │
        │ 1. "где сейчас EndpointId X?"   ┌──────────────────┐    │ публикует каждые N минут
        └────────────────────────────────►│ Address lookup   │◄───┘ подписанную запись:
                                          │ (pkarr / DNS)    │      {relay URL, IP:порты}
        ◄──── подписанная запись ─────────└──────────────────┘
        │ 2. QUIC через relay (работает сразу, за любым NAT)
        ├───────────────────► Relay ─────────────────────────────────►│
        │ 3. параллельно — UDP hole punching
        └══════════════ прямое P2P-соединение ═══════════════════════►│
```

* **Address lookup** хранит лишь подписанную ключом хоста запись «где я сейчас». Подделать её нельзя; это не база пользователей.
* **Relay** нужен для первичного рукопожатия и как запасной канал, если hole punching не удался. Пересылает только зашифрованные пакеты.
* При смене IP хоста посреди сессии QUIC мигрирует путь без разрыва.

### 2.1 Инфраструктура и независимость

| Этап | Lookup | Relay | Зависимость от третьих лиц |
|---|---|---|---|
| сейчас | публичный n0 DNS/pkarr | публичные relay n0 | бесплатная инфраструктура n0, без регистрации |
| v2 | + Mainline DHT (BitTorrent, BEP44) | свой `iroh-relay` на VPS (опционально) | ноль |

## 3. Модель доступа («синхронизация по ключу»)

### 3.1 Файлы

Каталог: `%APPDATA%\PandaRC\config\` (или `$PANDA_HOME`).

| Файл | Сторона | Содержимое |
|---|---|---|
| `host.key` | хост | Ed25519 SecretKey — постоянный «адрес» ПК |
| `host.json` | хост | `access_secret` (32 случайных байта), имя, необязательный PIN (соль + BLAKE3-хеш) |
| `connections.log` | хост | журнал подключений (JSON Lines) |
| `client.key` | клиент | ключ клиента (стабильный ID в журнале хоста) |
| `hosts.json` | клиент | сохранённые компьютеры: имя + билет |

### 3.2 Билет подключения (ticket)

```
panda1<base32( host_endpoint_id[32] || access_secret[32] )>
```

Одна строка (~110 символов), которую один раз переносят на клиент. Её достаточно, чтобы подключаться всегда, где бы ни был хост. Билет = пароль. `panda-rc host --rotate-secret` (или кнопка в GUI) делает все старые билеты недействительными, сохраняя адрес ПК.

### 3.3 Аутентификация

QUIC/TLS уже взаимно аутентифицирует стороны по ключам. Поверх — challenge-response без передачи секрета:

```
Клиент → Хост : Hello { version, client_name, profile: Desktop | Game, monitor: Option<u8> }
Хост → Клиент : Challenge { nonce[32], host_name }
Клиент → Хост : Auth { mac = BLAKE3-keyed(secret, "panda-rc auth v1" || nonce || client_id || host_id) }
Хост → Клиент : AuthResult { ok, reason }
```

Привязка MAC к обоим ID исключает replay/relay-атаки. Неудачная попытка → пауза 2 с + запись `auth_failed` в журнал.

**PIN-код (необязательно).** Если в `host.json` задан PIN, после верного MAC хост отвечает `PinRequired`, клиент шлёт `Pin(цифры)` внутри уже зашифрованного соединения с проверенным ключом хоста, хост сравнивает солёный BLAKE3-хеш. 5 неверных PIN подряд → PIN не принимается 5 минут ни от кого (счётчик в памяти хоста). PIN перечитывается из файла при каждом подключении — смена не требует перезапуска. Клиент без PIN получает `PinError`, GUI показывает окно ввода и подключается заново. Со службой PIN меняется через повышенный шаг `service set-pin --pin-file … --to <папка пользователя>`: PIN передаётся файлом в личной папке, не в командной строке.

## 4. Архитектура

Один бинарник `panda-rc.exe` на Rust. Один движок стриминга **Panda Stream** с двумя профилями:

| | Профиль «Рабочий стол» | Профиль «Игра» |
|---|---|---|
| Частота кадров | до 30 | 60 |
| Битрейт | 8 Мбит/с | 20 Мбит/с, адаптивный (5–50) |
| Мышь | абсолютная (курсор клиента) | относительная, курсор захвачен окном |
| Клавиатура | текст + шорткаты | сканкоды (как физическая клавиатура) |
| Геймпад / звук | — / да | да / да |

```
 ХОСТ                                                                 КЛИЕНТ
 DXGI Desktop Duplication ─► BGRA→NV12 ─► H.264 HW (Media Foundation:   QUIC datagrams ─► сборка кадра
   (кадр только при изменении)            QuickSync / NVENC / AMF;      + Reed-Solomon FEC   + восстановление FEC
                                           fallback openh264)                     │            ─► декодер H.264
 WASAPI loopback ─► Opus 20 мс ──────────────────────────► QUIC datagrams ─► Opus ─► динамики
 SendInput (сканкоды, отн. мышь) ◄── control stream ◄───── ввод: клавиатура, мышь, геймпад (gilrs)
 ViGEmBus (виртуальный Xbox 360) ◄─┘
```

### 4.1 Команды

| Команда | Что делает |
|---|---|
| `panda-rc` | GUI: «Компьютеры» (мои ПК, «Подключиться» / игровой режим) и «Этот ПК» (доступ, билет, PIN, автозапуск, обновления, журнал). Иконки — свои SVG (сетка 24, линия 1.75), растеризуются resvg и тонируются; шрифт Segoe UI из системы |
| `panda-rc host [--rotate-secret]` | headless-хост (для автозапуска) |
| `panda-rc ticket` | показать билет |
| `panda-rc pin <PIN\|off>` | задать или убрать PIN-код |
| `panda-rc connect <ticket> [--game]` | открыть окно сеанса |
| `panda-rc log` | журнал подключений |
| `panda-rc probe <ticket> [--game]` | диагностика: принять видео, сохранить кадр в PNG, показать fps и потери |

### 4.2 Модули

```
src/
  main.rs              CLI
  config.rs            ключи, host.json, hosts.json, журнал
  ticket.rs            билет
  proto.rs             сообщения, фрейминг, MAC, настройка endpoint
  media/fec.rs         нарезка кадров на датаграммы + Reed-Solomon
  service.rs           служба Windows: установка, надзор за хелпером в консольной сессии
  host/desktop_switch.rs  переход потоков на активный рабочий стол (Winlogon/UAC)
  host/mod.rs          приём соединений, auth
  host/session.rs      конвейер сеанса: захват → кодек → отправка, приём ввода
  host/dxgi.rs         захват DXGI Desktop Duplication
  host/capture.rs      источник кадров (DXGI → fallback GDI)
  host/encoder/        mf.rs — аппаратный H.264 (Media Foundation); sw.rs — openh264
  host/input.rs        SendInput: абсолютная/относительная мышь, сканкоды, текст
  host/gamepad.rs      виртуальный Xbox 360 через ViGEmBus
  host/audio.rs        WASAPI loopback + Opus
  client/mod.rs        подключение + auth
  client/viewer.rs     приём видео/звука, сборка кадров, отправка ввода и статистики
  client/decoder/      mf.rs — DXVA-декодер (Media Foundation); sw.rs — openh264
  yuv_render.rs        отрисовка NV12 шейдером wgpu в egui
  gui.rs               eframe/egui интерфейс
```

### 4.3 Соединение и каналы

Одно QUIC-соединение, ALPN `panda-rc/2`:

| Канал | Направление | Содержимое |
|---|---|---|
| bi-stream «control» (надёжный) | ↔ | auth; `Input`, `Gamepad`, `Draw`, `SecureAttention`, `RequestKeyframe`, `Stats` (клиент); `StreamInfo` (с подписями мониторов), `Rumble`, `SecureDesktop` (хост) |
| datagrams, тип `0x01` | хост → клиент | шарды видеокадров с FEC |
| datagrams, тип `0x02` | хост → клиент | пакеты Opus (20 мс) |

### 4.4 Видео

* **Захват**: DXGI Desktop Duplication — кадр только при изменении экрана, ~1 мс. Fallback GDI. При потере дубликации (UAC, блокировка, смена режима) — переоткрытие каждые 0,5 с.
* **Кодирование**: аппаратный H.264 через Media Foundation (асинхронный MFT, low-latency режим, CBR, IDR по запросу). Работает на Intel QuickSync, NVIDIA NVENC и AMD AMF через их MFT. Если аппаратного энкодера нет — openh264.
* **Транспорт**: кадр режется на шарды по размеру датаграммы, к ним добавляются Reed-Solomon parity-шарды (≈20 %, минимум 1). Заголовок шарда: `type u8 | frame_id u32 | idx u16 | data u16 | parity u16 | frame_len u32 | flags u8`. Клиент собирает кадр, как только пришли любые `data` шардов из `data+parity`.
* **Потери**: если кадр не собрался, а уже идёт следующий, — кадр отбрасывается, клиент шлёт `RequestKeyframe` (не чаще раза в 200 мс) и до IDR не декодирует.
* **Адаптивный битрейт**: клиент раз в секунду шлёт `Stats { frames, lost }`; хост снижает битрейт ×0,8 при потерях > 2 % и повышает ×1,1 после 5 с без потерь (в пределах профиля).
* **Декодирование**: Microsoft H.264 MFT, привязанный к D3D11-устройству (DXVA — декодирует видеочип); кадр копируется в staging-текстуру и читается одним Map. Если DXVA недоступен — openh264. Диагностика: `PANDA_DECODER=sw`.
* **Отрисовка**: кадр передаётся в GUI как NV12 (1,5 байта на пиксель), YUV→RGB (BT.601) считает фрагментный шейдер wgpu внутри egui. Без wgpu — конвертация на CPU и обычная текстура.

### 4.5 Ввод

* **Рабочий стол**: абсолютные координаты, нормализованные 0..65535; печатный текст — `Text`; спец-клавиши — `Key` с модификаторами.
* **Игра**: окно захватывает курсор, передаются сырые относительные смещения мыши → `SendInput(MOUSEEVENTF_MOVE)`; клавиши — по физическому положению → сканкоды `SendInput(KEYEVENTF_SCANCODE)`, это понимают игры на DirectInput/Raw Input. Выход из захвата: `Ctrl+Alt+Shift+Q`.
* **Геймпад**: клиент читает контроллеры через gilrs и шлёт состояние в раскладке XInput при каждом изменении; хост создаёт виртуальный Xbox 360 через драйвер **ViGEmBus** (единственный способ получить виртуальный XInput-контроллер в Windows; ставится один раз). Вибрация: драйвер ViGEm уведомляет хост о моторах, которые включила игра → `HostMsg::Rumble { large, small }` по control-потоку → клиент проигрывает постоянный force-feedback эффект (gilrs) на подключённых геймпадах до следующего изменения.

### 4.6 Звук

WASAPI loopback (то, что звучит на хосте) → 48 кГц стерео → Opus (CELT, low-delay) 20 мс, 128 кбит/с → датаграммы `0x02 | seq u32 | opus`. На клиенте: джиттер-буфер 40 мс (обрезка выше 150 мс), маскировка до 5 потерянных пакетов средствами Opus PLC, вывод через cpal. Opus — чистая Rust-реализация (opus-rs), сборка без CMake.

### 4.7 Служба Windows

Обычный процесс в сессии пользователя не видит экран блокировки и окна UAC: они живут на отдельных рабочих столах (`Winlogon`, secure desktop), доступ к которым есть только у SYSTEM. Поэтому:

```
 Служба PandaRemote (session 0, LocalSystem)
   │ раз в секунду: активная консольная сессия? хелпер жив?
   ▼ CreateProcessAsUser(токен службы, перенесённый в сессию N)
 panda-rc host --service-helper (SYSTEM, session N, winsta0\default)
   ├─ поток захвата и поток ввода перед работой вызывают OpenInputDesktop + SetThreadDesktop,
   │  поэтому DXGI и SendInput работают и на Winlogon/UAC
   └─ ключ, секрет, журнал — %ProgramData%\PandaRC\config (PANDA_HOME)
```

* Смена пользователя/выход/вход меняет консольную сессию — служба перезапускает хелпер в новой.
* `service install` (от администратора): проверяет права, назначает владельцем `%ProgramData%\PandaRC` администраторов, убирает наследование и оставляет доступ только SYSTEM и администраторам (по SID, работает в локализованной Windows), затем копирует `host.key`/`host.json` текущего пользователя — билет не меняется. Без этой блокировки обычный пользователь мог бы заранее подложить свой секрет и получить удалённый доступ уровня SYSTEM.
* Пока служба установлена, встроенный хост в GUI отключён (два хоста с одним ключом мешали бы друг другу на relay); `panda-rc host` отказывается стартовать при работающей службе.
* Установка из GUI: кнопка запускает `panda-rc service install` через UAC (`ShellExecuteEx` с `runas`); результат возвращается через временный файл.
* Экран блокировки: раз в 500 мс сеанс проверяет, заблокирован ли сеанс Windows (`WTSQuerySessionInformation`, на Windows 11 экран блокировки рисуется на обычном рабочем столе `Default`) или активен другой рабочий стол (UAC), и шлёт клиенту `HostMsg::SecureDesktop`. Пока он активен, клиент передаёт клавиши сканкодами (как физическая клавиатура), без Unicode-текста: экран входа Windows может не принимать синтетический текст, а сканкоды попадают в его собственную раскладку.
* Служба запускается из своей копии `%ProgramFiles%\PandaRC\panda-rc.exe` (копируется при установке, удаляется при удалении), чтобы не держать файл в папке сборки.
* Логи службы и хелпера и журнал подключений службы лежат в `%ProgramData%\PandaRC\logs`, который пользователи читают по наследованию; `config` с `host.key`/`host.json` им закрыт. Установлена ли служба, определяется по ключу реестра службы (его читают все), а не по файлу.
* Захват при смене рабочего стола перезапускается в новом потоке: поток, у которого уже есть окна (их может создать кодер), не может перейти на другой рабочий стол. Номера кадров продолжаются.
* Логи: `%ProgramData%\PandaRC\logs\service.log`, `helper.log` (обрезаются после 5 МБ).

### 4.8 Онлайн-статус, автозапуск, повторная блокировка

* **Онлайн-статус**: хост принимает отдельный ALPN `panda-rc/ping` — рукопожатие QUIC и сразу закрытие, без аутентификации и данных. Клиент раз в 20 с пингует все сохранённые компьютеры (таймаут 8 с) и показывает «в сети · P2P/relay, RTT» или «не в сети»; онлайн-компьютеры наверху списка. Хост старой версии отвергает этот ALPN на рукопожатии — это тоже считается «в сети».
* **Автозапуск**: значение `PandaRemote` в `HKCU\…\CurrentVersion\Run` (без прав администратора) с `--minimized`; указывает на копию в Program Files, если служба установлена. Галочка на вкладке «Этот компьютер», по умолчанию включено. `settings.json` пользователя хранит это и то, был ли включён встроенный хост — он поднимается при старте.
* **Повторная блокировка**: если за время сеанса сеанс Windows хоть раз был заблокирован, а к отключению зритель его разблокировал, хост вызывает `LockWorkStation` (запасной вариант — `WTSDisconnectSession`).

### 4.9 Рисование и обновления

* **Протокол 4** добавил: список кодеков клиента в `Hello`; кодек, флаг «только просмотр» и MAC-адреса хоста в `StreamInfo`; `ClientMsg::Clipboard/Message/Wake`, `HostMsg::Clipboard/FileSaved/Done`; профиль `Control` (без видео, один запрос — сейчас Wake-on-LAN); файлы — отдельные однонаправленные QUIC-потоки (`FileHeader { name, size }`, затем байты).
* **Кодеки**: клиент сообщает, что декодирует (H.264 всегда; HEVC — если есть декодер MFT), хост перебирает HEVC → H.264 и берёт первый, для которого есть аппаратный кодировщик; иначе openh264. Транспорт кадров от кодека не зависит (FEC режет кадры как байты, ключевой кадр — флаг кодировщика). AV1 исключён: кодировщик Intel даёт 45 мс на кадр 1080p (H.264 — 20, HEVC — 14), а его вывод не разобрал системный декодер AV1.
* **Билет для просмотра**: второй секрет `view_secret` в `host.json`, создаётся по запросу. MAC проверяется против обоих секретов (секреты перечитываются при каждом подключении). С билетом просмотра хост игнорирует ввод, геймпад, Ctrl+Alt+Del, буфер обмена и файлы и не даёт профиль `Control`; рисование и сообщения работают.
* **Буфер обмена**: только текст до 1 МБ. Обе стороны опрашивают свой буфер раз в 0,5 с и помнят последнее переданное значение, чтобы не отправлять его обратно. Содержимое буфера на момент начала сеанса не передаётся.
* **Файлы**: только с клиента на хост, до 4 ГБ, в «Загрузки\Panda» пользователя, вошедшего в сеанс (помощник службы работает от SYSTEM и получает папку через `WTSQueryUserToken` + `SHGetKnownFolderPath`). Имя очищается от путей и запрещённых символов, пишется во временный `.part`, совпадающие имена получают « (2)».
* **Сообщения на экран**: в том же прозрачном окне, что и рисование; текст растеризуется `ab_glyph` шрифтом Segoe UI, держится 6 с.
* **Запись**: на клиенте, принятые кадры без перекодирования. H.264 — MP4 (SPS/PPS из первого ключевого кадра в `avcC`, NAL-единицы с 4-байтной длиной, время — по часам прихода). HEVC — элементарный поток `.hevc`, потому что используемый MP4-писатель не хранит параметры HEVC. При начале записи хост показывает «Этот сеанс записывается».
* **Wake-on-LAN**: хост сообщает MAC своих сетевых карт (без виртуальных адаптеров VMware/Hyper-V/VirtualBox), клиент сохраняет их с компьютером. Разбудить можно через любой другой онлайн-ПК из списка: клиент открывает к нему соединение с профилем `Control`, тот шлёт «магический пакет» широковещательно на порты 9 и 7 своей сети.
* **Трей**: `tray-icon`. Окно прячется и показывается вызовами Win32 по HWND, потому что eframe не выполняет кадры скрытого окна. «Выход» завершает процесс.
* **Мониторы**: протокол 3. Клиент выбирает монитор в `Hello` (индекс в списке DXGI-выходов, `None` — основной), хост присылает подписи всех мониторов в `StreamInfo`. Смена монитора — переподключение: декодер на клиенте рассчитан на одно разрешение. Для неосновного монитора абсолютные координаты мыши пересчитываются в пространство всего виртуального рабочего стола (`MOUSEEVENTF_VIRTUALDESK`). GDI-запасной путь захватывает только основной монитор.
* **Только просмотр**: инструмент «глаз»; клиент перестаёт отправлять ввод и геймпад (фильтр в одном месте — очередь отправки), но отпускания клавиш и кнопок проходят, чтобы на хосте ничего не осталось зажатым.
* **Ctrl+Alt+Del**: `ClientMsg::SecureAttention`. Хост работает в процессе-помощнике в сессии пользователя, а `SendSAS` разрешён только службе, поэтому помощник шлёт службе пользовательский управляющий код 130, и служба вызывает `SendSAS(FALSE)` из `sas.dll`. Установка службы включает политику `SoftwareSASGeneration` = 1 (только службы), если она ещё не разрешает этого. Без службы кнопка ничего не делает.
* **Рисование**: в окне сеанса инструменты «перо» и «указка». Клиент шлёт `ClientMsg::Draw` (точки штриха, конец штриха, позиция указки, очистка) и сразу рисует ту же модель у себя. Хост рисует её tiny-skia в прозрачном окне поверх всех (`WS_EX_LAYERED | WS_EX_TRANSPARENT | WS_EX_TOPMOST`, клики проходят насквозь), окно исключено из захвата (`WDA_EXCLUDEFROMCAPTURE`), чтобы зритель не видел линии дважды. Штрих гаснет за 1 с после отпускания кнопки.
* **Обновления**: GitHub Actions по тегу `v*` собирает `panda-rc.exe` и подписывает ed25519 сообщение `"panda-rc release <версия>
" || exe` ключом из секрета `PANDA_SIGNING_KEY`; публичная половина встроена в программу. Клиент и служба проверяют `releases/latest` при старте и раз в 6 часов, скачивают, проверяют подпись (с версией — защита от подсунутой старой сборки) и ставят: приложение — при перезапуске, по кнопке или само без активного сеанса; служба — заменяет свою копию в Program Files и перезапускается отдельным процессом. Окно, запущенное из Program Files, замечает подмену файла и перезапускается.

### 4.11 Почему так

* **Датаграммы + FEC, а не надёжный поток**: при потере пакета надёжный поток ждёт ретрансмит (≥1 RTT) и задерживает все следующие кадры; FEC восстанавливает потерю сразу, а неисправимая потеря стоит одного IDR.
* **Media Foundation, а не NVENC/AMF SDK напрямую**: один API для всех трёх вендоров, без проприетарных SDK.
* **QUIC (iroh)** даёт шифрование, NAT traversal и congestion control.

## 5. Безопасность

| Угроза | Защита |
|---|---|
| Прослушивание (провайдер, relay) | QUIC TLS 1.3, сквозное шифрование |
| Подмена хоста | соединение по EndpointId — TLS проверяет ключ хоста |
| Подмена записи «где хост» | запись подписана ключом хоста |
| Подбор секрета | 256 бит энтропии + пауза после неудачи |
| Утечка билета | смена секрета; PIN-код поверх билета; журнал показывает все попытки |
| Подбор PIN | 5 попыток, затем блокировка на 5 минут; пауза 2 с после каждой ошибки |
| Злоупотребление вводом | ввод принимается только после успешной аутентификации |
| Утечка секрета в логи | `Debug` обработчика хоста не печатает секрет |

## 6. Ограничения текущей версии

* Без установленной службы хост работает в сессии пользователя: экран блокировки и окна UAC недоступны. Со службой — доступны (п. 4.7).
* Ctrl+Alt+Del (SAS) пока не отправляется; на Windows 10/11 экран блокировки открывается кликом или клавишей, поэтому обычно не нужен.
* Курсор удалённого ПК в кадр не рисуется (в профиле «Рабочий стол» виден локальный курсор клиента).
* Один (основной) монитор; при смене разрешения нужно переподключиться.
* Геймпад требует установленного драйвера ViGEmBus на хосте.
* Две копии клиента на одном ПК делят `client.key` и мешают друг другу на relay.
